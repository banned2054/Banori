# 下载系统业务基准（DOWNLOAD_BUSINESS_RULES）

> 最后核对：2026-11-11，基于当前工作区未提交实现；未提交/未发布。
>
> 本文是下载系统唯一业务基准，只回答“业务要求是什么”。现状证据见 [DOWNLOAD_ARCHITECTURE_AUDIT.md](DOWNLOAD_ARCHITECTURE_AUDIT.md)，取舍见 [DOWNLOAD_ARCHITECTURE_DECISIONS.md](DOWNLOAD_ARCHITECTURE_DECISIONS.md)，剩余目标见 [DOWNLOAD_TARGET_ARCHITECTURE.md](DOWNLOAD_TARGET_ARCHITECTURE.md)。三份文档与本文冲突时以本文为准，不得用实现反推修改本文。
>
> 分级：**【用户明确】**= 用户直接给出的规则；**【已确认的边界决定】**= 为落地规则已确认的边界，不是新增规则；**【实现选择】**= 当前实现已采纳、用户尚未逐条确认的边界，不是规则；**【仍待用户决定】**= 尚未定案，实现当前的选择不得当作规则。

## 1. 来源分类：由入口决定

| 入口 | 判定依据 | 结果 | 级别 |
|---|---|---|---|
| RSS（一次性/订阅） | 只按实际 RSS 地址主机 | `mikanani.me`、`mikanime.tv` 同为 `mikan`；`anibt.net` 为 `anibt`；种子内 tracker 不得覆盖 | 【用户明确】 |
| RSS 未知主机/地址无法解析 | 不猜域名首段，不猜公共站点 | 内部竞争域 `(unknown)`；展示标签 `SiteSource` 保持空 | 【已确认的边界决定】 |
| 上传 `.torrent` | 只按已知 tracker 的主机名+路径精确匹配 | U2=`daydream.dmhy.best/announce`；BYRBT=`tracker.byr.pt/announce.php`；TJUPT=`tracker-public.tjupt.org` 或 `tracker-campus.tjupt.org` 的 `/announce.php` | 【用户明确】 |
| 上传未命中任何已知 tracker | 含仅有公共 tracker、相似域名、错误路径 | 统一归 `other`，不是 `bt`，也不按公共 tracker 推断 | 【用户明确】 |
| 上传 AniBT 种子 | 当前无真实 announce 主机/路径 | 不猜，仍归 `other`；与 AniBT RSS 的 `anibt` 分属不同域，直到 U1 提供真实值 | 【用户明确】+【仍待用户决定】 |
| 一个种子命中多个不同已知分类 | 去重后分类数 >1 | 拒绝登记，不按 tracker 顺序取第一个 | 【用户明确】 |
| 同一分类的多个 tracker 地址 | 去重 | 仍只算一个分类 | 【已确认的边界决定】 |

- **来源作用域 `SourceScope` 是竞争键，展示标签 `SiteSource` 只用于展示、命名与下载器 tag。** 任务行不新增来源列，作用域由入口写入或由 `SiteSource` 归一推导。
- 【已确认的边界决定】哨兵固定为：`(legacy)`（迁移前/无法证明的旧行，不参与已知来源竞争）、`(unknown)`（未知 RSS，所有未知 RSS 同域）、`other`（未知上传，所有未知上传同域）。`(unknown)` 与 `other` **永不互相竞争**。
- 已知来源值写前 `trim + 小写`；历史 `bt` 读取归 `other`，历史 `U2` 读取归 `u2`。空值读取为 `(legacy)`；写入永不产生 NULL。
- 【已确认的边界决定】`other` 与 `other` 互为同源；`(unknown)` 与 `(unknown)` 互为同源；`(legacy)` 不与任何已知来源或哨兵竞争。
- 【已确认的边界决定】qB tag 与命名只使用 `SiteSource`；哨兵 `(legacy)`/`(unknown)` 不进入展示与命名。未知 RSS 当前不写 tag，`other` 当前会写 tag；这是实现现状，不构成业务规则。

## 2. 竞争域与复用边界

- **只有来源作用域相同的候选才参与版本竞争。** 动画、集数、字幕组、语言、版本、文件大小、文件内容全部相同，只要来源作用域不同，也不对决、不互相顶替。 【用户明确】
- 跨来源可以复用同一份磁盘文件；复用是文件数据判断，不是竞争关系，不得因此把两个来源放进同一竞争域。 【用户明确】
- 文件复用判断独立于版本竞争；复用结果不得改变竞争胜负，竞争也不得阻止跨来源复用。 【用户明确】
- 动画身份优先用条目/字幕组解析出的 `SubjectId`；无 Subject 时按归一化标题互认；无法互认时宁可重复登记，不凭猜测淘汰。 【已确认的边界决定】
- 集数取文件级合成集数：人工覆盖 > 修正后的文件名解析；合集区间文件不拆；无法解析集数的文件不参与逐集竞争。 【已确认的边界决定】
- 【仍待用户决定】同一 info-hash、不同来源是否允许并存。当前上传入口按 hash 全局查重（不按来源过滤），第二个来源会被拒绝。见 U2。

## 3. 版本、平级与逐文件裁决

- 字幕组、语言优先级继续使用现有规则配置；未命中规则按现有 `UnmatchedPolicy` 处理。 【已确认的边界决定】
- **版本号只在同字幕组、同语言内构成升级。** 不得让某字幕组的 v3 跨越另一个字幕组，也不得让同组不同语言凭版本号升级。 【用户明确】
- **平级候选按两层归约决胜。**（2026-11-11 用户明确）在规则优先级最高的候选层内：先按**字幕组（忽略大小写）+ 语言（精确）**分区；分区内按**版本 → 初始候选正片数 → 发布时间 → 稳定标识**选出分区冠军；分区冠军之间按**初始候选正片数 → 发布时间 → 稳定标识**选全局冠军。
- **版本只在同一分区内比较**；不得按字幕组名或语言名排序决胜。因此跨字幕组/跨语言的同优先级候选，按初始候选正片数决胜。 【用户明确】
- **优先级相同时，单集与合集优先合集；合集之间按初始候选正片数口径比较。** 组合/通配规则造成不同字幕组、不同语言同优先级时，不得由“保留现任”阻止合集优先。 【用户明确】
- **现任（已登记优胜）仅当全局冠军的初始候选正片数严格更多时才被替换；计数相同时保留现任一侧的分区冠军**（现任本身，或其分区内版本/计数更高的升级者）。 【用户明确】
- 初始候选正片数只数 `Anime` 正片，不含字幕与 `Seed`；跨包落选只改选择状态、不改变文件角色，因此计数不随逐集裁决结果缩小。单集 vs 合集、合集 vs 合集适用同一口径；不允许用“原始 torrent 文件总数”代替。 【用户明确】
- **不做胜者全取（实现选择，不是用户规则）。** 每一个对应集的文件独立裁决；平级决胜后，胜出包只保留自己胜出的文件，落选包只取消对应落选文件，不把整包文件成组判给胜者。用户已明确的是“部分文件落选只取消对应文件”的逐文件语义；用户未确认“胜者全取”，也未把“不做胜者全取”确认为规则。 【实现选择】
- 部分文件落选时，只取消对应文件的下载选择并保留下载器中的 torrent；不得因部分落选删除整包。 【用户明确】
- 只有当一个多文件 torrent 的全部内容文件都不再承担下载职责时，才允许整包退出；退出种子默认不删磁盘数据，磁盘删除只能由用户显式操作。 【用户明确】
- 【实现选择】`AllContentLost` 当前把字幕算作内容（不含 `Seed`）；字幕是否计入整包退出是当前实现口径，不是用户逐条确认的规则。
- 【实现选择】两条决胜链的末尾兜底仍是 `FeedItemId`（数据库 ID），仅在前面的键全部相同时生效；是否改为内容键见 U5。
- 【仍待用户决定】“包含承接”是当前实现的窄例外：已完成现任与挑战方同集正片同名同大小时，可被覆盖面更大的新包翻转。它不在本基准内，是否保留见 U3。

## 4. 保存路径与替换

- 存在同来源、同集、低优先级的待替换版本时，新版本先下载到**临时目录**，不进入正式根，不覆盖正在使用的旧文件。 【用户明确】
- 不存在上述待替换版本时，直接下载到正式目标目录；不得无条件创建临时目录。 【用户明确】
- 新版本完成并确认后，才执行迁移/替换；旧文件只有在不再承担任何职责后才允许清理。 【用户明确】
- 目标路径冲突时保护原文件：不覆盖、不猜测、不静默改名；冲突交由占用检查与人工核对处理。 【用户明确】
- 临时目录只用于“替换暂存”；复用校验的候选根是正式根，不得因为要校验就改走临时目录。 【已确认的边界决定】

## 5. 已有数据复用

- 复用可以跨来源，也可以针对下载器中未登记的种子；不得只靠 info-hash 判断，**不同 hash 不能成为排除复用的理由**。 【用户明确】
- 目标路径 + 文件大小只是候选线索，不是内容证明；必须由**停止状态下的受控映射**和 **recheck 逐文件结果**确认。 【用户明确】
- 同一 torrent 内以文件清单中的稳定文件身份匹配；**不同 torrent 的相同文件 index 不可假定为同一文件**，qB index 每次现算、不持久化。 【用户明确】
- 无法确认时保护已有数据：不得断言损坏、不得删除；必要时转为独立下载（隔离重加），旧数据留在原处。 【用户明确】
- 复用证实后写 `ReusedVerified` + 绑定路径；路径/大小/选择任一变化即降级或作废，不得沿用旧证据。 【已确认的边界决定】

## 6. 校验三态与做种

- 校验结果必须能区分三态：**校验未确认**（执行或结果未知）、**数据不完整**（已确认缺失）、**操作失败**（改名/移动/身份/提交等失败）。 【用户明确】
- 校验未确认时：任务保持暂停，保留候选映射、文件与种子；不隔离、不删种、不删磁盘、不自动重下；用户可“重新校验”，重发 recheck 而不放弃复用。证据强度不影响保护力度：无法证明本轮请求已作用于该种子时，保持未确认，不得凭 HTTP 成功或进度 100% 推断校验已完成。 【用户明确】
- `checkingResumeData` 不构成内容校验证据；这是统一规则，没有“请求刚发出”的例外窗口。 【用户明确】
- 数据不完整时：按确认缺失处理，转隔离独立下载；旧文件保持原样。 【用户明确】
- 操作失败时：进入失败/人工处理，保留可恢复信息；不得把操作错误伪装成数据损坏。 【用户明确】
- **数据完整与做种/继续下载恢复是两个独立问题，分开回答：** 文件是否完整（校验结果）、种子是否恢复（恢复状态）、在等什么/如何恢复（等待原因与下一步）三者互不混用。 【用户明确】
- 数据完整性确认后自动继续做种，**不重复下载**；`Resume`/`Reannounce` 失败不否定已确认的数据完整性，也不得因此重校验、隔离或重下。 【用户明确】
- 恢复请求响应丢失时，先观察下载器的实际状态再处置；不得凭“响应丢失”直接判定失败或无界重发。 【用户明确】
- 从 qBittorrent 删除种子 ≠ 删除磁盘文件；自动链恒 `deleteFiles=false`。 【用户明确】

## 7. 计数与口径说明

- 本基准中的“初始候选正片数”= **逐集裁决前**该包在 torrent 内的 `Anime` 正片文件数；不含字幕、不含 `Seed`、不含包内已被判为 `Seed` 的落选变体。
- 该数是平级决胜输入，不是“最终保留数”，也不是裁决后的选中数；禁止把它写成 `DC_opt`、`FinalDC` 或任何“最终胜出文件数”的等价物。
- 跨包部分落选不会减少该数；同一包在后续对局中使用同一初始值，因此结果不依赖登记顺序或逐集处理顺序。

## 8. 旧任务交接与回填

- 旧任务交接**不丢关系**：已登记的现任/落选/待完成关系不得因迁移静默消失。 【用户明确】
- 能确定来源的旧登记**尽量迁移**到对应来源作用域；无法确定来源的**明确报告**，不猜、不静默丢弃。 【用户明确】
- 回填必须**幂等**：重复运行结果一致，已迁移的槽不重复迁移、不重复成行。 【用户明确】
