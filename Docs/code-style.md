# .NET / C# 代码排版约定

本文件记录用户明确表达、需要结合语义和函数整体布局判断的 C# 排版偏好。
机械格式继续采用项目的 `.editorconfig` 与 solution team-shared `.DotSettings`；这里不是另一份工具配置，
也不声称这些偏好全部无法通过工具表达。AI 应在写代码和检查实际 diff 时落实这些约定。

用户当前明确要求优先于历史样本。已有源码含多种排法，不能把工具自动换行、过去 AI 的写法
或个别例外全部推断为用户有意选择。不借排版改变逻辑、拆方法、添加临时变量或扩大修改范围。

## 1. 先看整个函数，再决定在哪里换行

- 默认保持相关表达式的整体性；短而清楚的调用、访问链、条件不主动拆成多行。
- 换行是为了看清结构、分组或满足有效行宽，不是为了让每个 token 或每次调用各占一行。
- 同时考虑函数的纵向长度、续行的起始列和横向空间。不能只看某一行是否低于字符上限，
  也不能为了减少行数把长表达式强行挤回一行。
- 不擅自另定一个统一字符数代替审美判断。遵守当前有效设置的行宽；行宽足够也不代表一行
  塞下所有逻辑就更易读。
- 空行用于区分执行阶段和逻辑段落，不在每次调用或简单语句后机械添加。
- 用户主动选择的折行应尽量保留，尤其是折行后右侧能完整呈现的赋值或返回表达式。
  不确定时结合相邻布局判断，不为了统一形状反复拆开又合并。

## 2. 调用参数：首参数靠近左括号，后续参数对齐

普通调用能清楚放下时，首参数和左括号保持同行；不默认在左括号后立即换行。
需要多行时，后续参数与首参数对齐，不替换成另一套统一缩进，也不无故再向右缩进。

```csharp
var result = CreateResult(sessionId, turnId);

var result = CreateResult(sessionId,
                          turnId,
                          executionRecords,
                          cancellationToken);
```

函数定义可以采用左括号后换行的形式。用户主动安排的布局，以及有效格式设置确实要求的
被动折行，也可以例外；“左括号后不换行”是默认偏好，不是不可违反的语法禁令。

参数列对齐可能占用较多横向空间，保留这项偏好。但如果整个右侧因此被挤得支离破碎，
可以在赋值右侧或返回表达式开始处选一个自然断点，再让右侧保持完整：

```csharp
var executionResult =
    CreateResult(sessionId, turnId, executionRecords, cancellationToken);
```

是否使用这个断点由当前函数的布局决定，不自动把所有赋值改成两行。

## 3. 成员访问与链式调用：按语义分组，不做阶梯

短的 `A.B.C` 保持完整；不能仅因存在多个点号就拆行。

```csharp
var name = session.Model.ModelId;
var ids  = records.Select(record => record.Id).ToArray();
```

较长的链按语义步骤或步骤组换行。不要强制每个访问、每个短调用、每个终结调用都独占一行，
也不要把续行逐层推向右侧。换行后相邻的点号保持稳定对齐；默认参考已有代码的行首点号，
这只是既有排法的参考，不把用户未明确指定的所有点号细节上升为硬规则。

```csharp
var ordered = documents.OrderBy(document => Depth(document.ScopeDirectory))
                       .ThenBy(document => document.SourcePath, StringComparer.Ordinal).ToArray();
```

`ThenBy(...).ToArray()` 可以作为同一语义组保留，不需要为了整齐强拆 `ToArray()`。
同理，`await`、调用、参数及 `.ConfigureAwait(false)` 应一起考虑：能连贯放下时保持完整，
确实太长时选自然边界，不机械拆散为多个越来越靠右的片段。

## 4. 长条件：一行一个条件，连接符在行尾

短条件仍保持一行。一旦因为长度或可读性拆行，默认每行一个完整逻辑条件，
将连接下一条件的 `&&` 或 `||` 放在上一行末尾，续行条件对齐：

```csharp
if (hasSession &&
    matchesIdentity &&
    hasCompleteHistory &&
    isWithinBudget)
{
    ContinueRun();
}
```

不要把连接符改到行首，不在已经拆行时为了填满行宽又把多个独立条件塞回同一行。
这里的“一个条件”指可独立理解的条件单元，不是把条件内部的方法参数也全部拆开。
有混合 `&&`／`||`、括号、模式匹配或注释时，先保持原有分组、优先级和短路语义，
再在同层条件边界折行；不能为了排版增删分组或重新排列条件。

## 5. 简单方法与初始化器

方法体只是一个简单 `return`、且没有需要保留的语句块、指令或说明时，优先使用 `=>`。
不要为了使用表达式体把多步骤方法压成复杂表达式，也不要删掉有意义的局部说明。

返回对象初始化器时，能放下的函数头和 `=> new()` 保持同行，花括号和属性采用正常块缩进；
不要让整个初始化器跟着表达式起始列移到屏幕右侧：

```csharp
private static Options CreateOptions() => new()
{
    Model         = "example",
    MaxAgentSteps = 8
};
```

同一小组内的类型、变量、赋值或属性可保留已有列对齐；不要跨不相关的逻辑段落为了对齐
制造大片空白。函数头或表达式确实过长时允许折行，不为追求这个示例的形状牺牲可读性。

## 6. using 与工具清理的分工

用户偏好命名空间按字母顺序排列，不把 `System` 自动提升到最前。使用工具前，核对该项目
实际的 cleanup profile；保留 using 原顺序不等于已经执行字母排序。
不要为运行清理擅自替换项目选定的 profile，或把 using 重排夹带到不相关修改。

工具清理之后，AI 仍需看整个受影响函数和前后 diff，检查链式表达式是否被拆散、参数列
是否过度占用横向空间、条件是否一行一个、初始化器是否整体向右漂移。
纯空白整理与 `return` 转表达式体等语法清理分别核对，不能把所有 cleanup 都称为纯格式化。

如果某个具体规则与 formatter 的结果冲突，明确指出冲突并在任务范围内决定处理方式；
不要静默修改共享设置，也不要不断重复清理使人工排版来回变化。

## 项目补充

- 本项目的机械格式来源是仓库根目录的 `.editorconfig` 与 `Banori.sln.DotSettings`；
  两者冲突时以 `.editorconfig` 为准。保留现有配置，不从其他项目复制工具选项或猜测 JetBrains 设置键。
- 按 `.editorconfig` 保存为 UTF-8 无 BOM、LF 换行，删除行尾空白，并保留文件末尾换行。
- 未在项目有效设置中规定的行宽，不另行指定统一字符数；结合整个函数和邻近布局判断。
- 本约定适用于当前任务涉及的 C# 代码。EF Core 迁移 Designer、模型快照等生成代码沿用生成器布局，
  不为满足人工排版偏好额外重排；代码排版任务也不扩展到无关的 Razor、样式、配置或历史代码。
- 本文件是项目内唯一的完整排版约定。其他 Agent 的项目指令应明确要求读取本文件，
  不另复制一份正文；是否自动加载须按实际使用的工具确认。
