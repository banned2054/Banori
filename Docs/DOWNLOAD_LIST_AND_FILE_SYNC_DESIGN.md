# 下载任务列表与文件同步设计

> 设计稿，2026-11-24

下载页采用无页码的虚拟滚动列表。业务状态随 Banori 的对账结果更新，打开的文件面板直接跟进 qBittorrent 路径。第一阶段交付列表、路径重绑和改名确认，验收通过后再接入主表进度的 `rid` 增量。

## 现状与 qB WebUI 参考

qB WebUI 的 `dynamicTable.js` 只渲染可视区及缓冲行。主表由 `client.js` 使用 `sync/maindata` 的 `rid` 获取增量，前台初始间隔为 1.5 秒，随后跟随服务端设置。`prop-files.js` 通过 `torrents/files` 每 5 秒读取当前种子的完整文件清单，面板收起、切走或页面隐藏时跳过请求。

Banori 当前主表每 15 秒读库，后台空闲对账间隔也是 15 秒，两段等待可能叠加。后台文件同步会在 qB 保存根与数据库记录不一致时退出。已完成任务的文件面板在同一个页面状态里只自动尝试一次，失败也占用这次机会。改名待确认时，页面每秒只读本地待处理标记，直到后台对账清除标记才再查一次 qB。 [下载页轮询](../Banori/Components/Pages/Downloads/Downloads.razor) · [文件面板状态](../Banori/Components/Pages/Downloads/DownloadTasksPageViewModel.cs) · [路径刷新](../Banori/Features/Downloads/DownloadFileService.cs)

## 无页码列表

- 移除顶部与底部的页码、上一页和下一页，列表保留匹配总数。顶部筛选和表头对应完整结果，沿用现有状态归组、语言筛选、排序与同值时的任务 ID 排序规则。
- 用有序任务 ID 快照表示当前筛选结果，快照长度就是匹配总数。滚动时按索引取视口和缓冲范围的 ID，只读取这些任务的行摘要。种子字节和逐文件信息由需要它们的操作或详情面板按需读取。
- 用固定行高和缓冲区控制挂载行数，滚动条可直达完整结果的任意位置。进度等展示字段变化时按任务 ID 更新行。任务增删、筛选结果成员变化或排序键变化时重建有序快照。主动更改筛选或排序时回到顶部，后台更新时以仍在结果中的可见任务 ID 恢复滚动位置。迟到的旧条件查询按请求序号丢弃。
- 选中项、底部详情和文件编辑草稿按任务 ID 管理。详情有独立的加载入口，选中行滚出视口时仍可查看和编辑。批量勾选跨滚动保留，首版将「全选本页」改为「勾选可见行」，范围取点击时视口里的任务，确认操作前显示实际选中总数。

当前查询已经将排序键和整页记录分开读取，但会为每次分页重做排序，并加载整页关联文件。虚拟列表复用相同的全局排序口径，将有序 ID 和滚动范围内的行查询分开。 [当前列表查询](../Banori/Features/Downloads/DownloadTaskQueries.cs)

## 刷新节奏

| 场景 | 初始间隔或触发点 | 数据与页面行为 |
| --- | --- | --- |
| 打开下载页、回到前台 | 立即 | 读取当前筛选下的可见窗口。已展开的文件面板同时发起一次同步 |
| Banori 任务状态与归档结果 | 数据库提交成功后通知页面，前台每 15 秒兜底 | 按任务 ID 更新可见行和选中详情。影响筛选或排序时重建快照。后台对账按既有调度采集状态 |
| 主表运行进度 | 第一阶段随数据库刷新，第二阶段约 2 秒 | 第二阶段使用按下载器共享的 qB 增量快照更新关联任务的进度 |
| 展开的文件列表 | 打开或切换任务时立即读取，随后每 5 秒 | 只读选中任务对应的 qB 种子。已完成且仍有明确关联的任务同样参加 |
| Banori 刚提交改名或移动 | 立即确认，待确认期间约 1 秒采样 | 由现有对账链核对目标路径。确认成功时使用同一结果写库、更新界面并开放再次提交 |

每一类轮询都在上一次完成后安排下一次，同一对象的在途读取合并。收起面板或切到其他标签时结束该面板的读取。页面隐藏或离开时暂停前台刷新，后台按已提交的意图继续对账。切换任务时丢弃旧任务的迟到结果。

临时查询失败时显示最近一次确认的数据，由后续自动读取重试。文件面板仍打开时，已完成任务同步失败也可自动恢复。若展示最近同步时间，以成功取得有效数据的时刻为准。文件记录的更新时间只在路径实际写回时推进。

## 外部换路径后的重绑

当已完成任务在 qB 中改过文件名、子目录或保存位置时，文件面板自动对账。接纳新根的条件是 qB 已下载完整、保存位置稳定且任务归属明确，包含下载完后已暂停的任务。同根改名继续用相同的文件身份校验。本轮重下、校验或布局变更尚待确认时，优先按对应的操作记录对账。

1. 按当前下载器和有效任务关联查找同一个 InfoHash，读取 qB 的保存根和移动状态。使用原始种子元数据计算 qB 文件 `index`，按显式 `index` 和字节数匹配现有文件记录。检查清单完整性、索引与路径唯一性以及相对路径合法性。
2. 读取清单后再次核对 qB 保存根。两次读到同一个规范化后的新根，且 qB 在两次读取中都已停稳时，才采纳这份映射。在现有协调门内重核下载器、任务归属、待处理操作和已知路径占用，再提交。
3. 在同一次数据库提交中更新任务的 `SavePath` 和逐文件的 `CurrentRelativePath`。更新前先计算旧的当前绝对路径和已发布绝对路径。此前两者指向同一份文件时，同步写入 `PublishedRelativePath` 和 `PublishedPath`。独立的已发布副本以原绝对路径固化，兼容通过旧根推导发布位置的存量记录。
4. 提交成功后返回新布局。qB 仍在移动、读取失败或两次保存根不一致时，保留上次确认布局并继续观察。文件身份无法匹配时报告具体原因。按 hash 确认缺种时交由现有缺种巡检与恢复流程处理。

例如在 qB 对已完成并暂停的种子使用「设置位置」后，Banori 仍记着 `/downloads`。文件面板读到稳定的新根并通过校验后，即可在原任务上自动恢复绑定。相关规则沿用现有种子索引计算、逐文件发布路径和改名对账。 [索引计算](../Banori.Core/Torrents/TorrentDownloadPolicy.cs) · [本轮布局与发布路径](../Banori/Features/Downloads/DownloadRoundLayout.cs) · [下载业务基准](DOWNLOAD_BUSINESS_RULES.md)

## Banori 发起改名后的确认

提交前持久化当前路径和目标布局，再发送 qB 改名或移动请求。请求返回后立即回读，若 qB 已显示全部目标文件路径且保存根已确认，直接写库并返回新路径。否则唤醒现有对账 worker，按约 1 秒的准备阶段间隔观察同一笔操作。

等待期间，文件面板继续显示 qB 观测和确认状态。待确认的任务由快速对账提供观测，面板复用同一份结果。后端确认完整计划后，页面直接采用已写回的新布局。此时开放再次提交改名、移动等冲突操作。路径变化使基于旧位置的预览失效，草稿输入按文件身份保留。

现有 30 秒布局确认窗口用于限制同一请求的补发，窗口内仍可观察和确认。请求耗尽预算时报告待核对的原因，已打开的面板回到 5 秒观察。后续看到目标时仍可依据持久化的操作记录确认。页面离开、请求超时和进程重启均使用这份记录恢复确认。 [异步生命周期与重试规则](QBITTORRENT_ASYNC_LIFECYCLE_PLAN.md) · [后台对账调度](../Banori/Workers/DownloadReconcileWorker.cs)

## 分阶段实施与验收

### 第一阶段 无页码列表与文件自动同步

交付虚拟滚动、列表行摘要、按任务 ID 加载详情、业务状态写库后的刷新和 15 秒兜底。文件面板使用现有 qB 种子状态和文件清单接口，交付 5 秒自动同步、失败重试、稳定换根重绑，以及改名提交后立即确认和约 1 秒的短间隔观察。

| 验收场景 | 通过条件 |
| --- | --- |
| 1 万条任务 | 记录首屏耗时和挂载行数。挂载行数随视口和缓冲范围变化。可拖到列表末尾，筛选与排序覆盖完整结果 |
| 滚动中有任务变化 | 选中详情、文件草稿和已勾选 ID 跟随原任务。筛选变化后的旧结果被丢弃 |
| 已完成并暂停，外部改名或换根 | 打开文件列表后自动匹配新路径。清单即使以不同顺序返回，也按种子索引绑定到相同文件记录。根与路径在同一提交中生效 |
| 换根期间正在移动，或同步暂时失败 | 页面保留最近一次已确认路径。移动结束或查询恢复后自动同步。独立归档路径继续指向原副本 |
| 换根时种子归属、文件索引或大小对不上 | 给出具体原因，文件面板继续展示已确认布局 |
| Banori 改名单文件或移动整颗种子 | qB 返回已确认目标后由同一结果更新页面和数据库，并开放再次提交。延迟和重启场景可继续对账 |
| 收起文件面板、切任务或切到后台 | 只对前台打开的选中任务发起文件轮询，迟到响应与其任务 ID 匹配后才能应用。后台仍会收尾已提交的操作 |

### 第二阶段 主表接入 rid 增量

第一阶段的万级列表、换根和改名确认场景验收通过后接入。每个已配置的下载器共享一个 `sync/maindata` 会话和一份快照。前台需要运行进度时以约 2 秒为初始间隔，同次采集供打开的页面复用。

- 首次读取使用 `rid=0`。收到 `full_update` 时重建快照。普通响应按 hash 合并返回的字段，并处理 `torrents_removed`。应用成功后才推进 `rid`。会话重建、配置更换或增量无法续接时重新取全量。
- 增量驱动归属明确的活跃任务的 qB 运行进度。Banori 的完成、归档、替换与缺种按已持久化的业务状态显示，文件页按选中任务读取 `torrents/files`，归档和改名写入由现有确认链判断。
- 用首次全量、部分字段变化、种子移除、断线重连、配置切换和多页面共用会话验收。记录同步请求数、返回体量和可见进度延迟，再调整初始间隔。
